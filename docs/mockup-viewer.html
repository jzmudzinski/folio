Research · AI / ML

RAG vs Fine-Tuning

Kiedy retrieval-augmented generation bije fine-tuning, a kiedy odwrotnie. Krótkie porównanie z 2026, z perspektywy małego SaaS budującego customer support i wewnętrzne narzędzia.

TL;DR

RAG wygrywa gdy: świeże/zmieniające się dane, low-latency mniej krytyczne, chcesz audytowalności źródeł. Fine-tuning wygrywa gdy: stabilna domena, specyficzny ton/styl, niskie latency w real-time, koszty inference dla high-volume use case.

Kiedy RAG

Klasyczny przypadek: docs Q&A. Twoja dokumentacja zmienia się co tydzień, modele językowe ma cutoff 2 lata wstecz. Building retrieval pipeline (chunking + embeddings + vector search) jest tańsze niż retraining za każdym razem gdy zaktualizujesz docs…

Co tu widać

  • Sidebar wstrzykiwany przez middleware — sama notatka jest niezmieniona na dysku. Viewer dorzuca chrome tylko gdy serwuje przez folio serve; jeśli ktoś otworzy plik bezpośrednio (file://), zobaczy czysty content.
  • Expiring banner z [Finalize] CTA — najsilniejsze remindery są w miejscu gdzie user właśnie czyta. Jeden klik = uratowanie noty.
  • "v1 z 3" w sidebarze → klik zabiera do thread view (state 03).
  • Status pokazany wprost — wygasa za 28 dni, w żółtym. User wie zawsze co się stanie.
  • Actions skupione w sidebarze — Finalize (primary), Publish (regular), Export standalone (rebuild dla share .html), Move to trash (danger).
  • Treść po prawej = czyste HTML, jak każda inna nota Folio. Theme.css współdzielony z viewer chrome — wszystko wygląda jak rodzina.

05 Notatki do implementacji (S1+S2)

Stack

  • Bez React, bez build step. Server-rendered HTML z Bun.serve + vanilla JS (~200 LOC dla live search + filter state).
  • SSE /sse wysyła note:created/updated/deleted → viewer JS reload listy bez F5 (file watcher z ADR-014 storage).
  • Theme.css współdzielony z notatkami (ADR-012 hosted profile). Viewer to po prostu kolejna „strona" w theme'ie.
  • Search jest synchroniczny GET — FTS5 wystarczy szybki (<10ms), nie potrzeba debounce/instant. Submit on enter.

Routes (z TODO S1)

  • GET / — Browse (state 01)
  • GET /search?q=&type=&status= — Search results (state 02)
  • GET /t/:thread_id — Thread view (state 03)
  • GET /n/:id — Note view z sidebarem (state 04)
  • POST /api/notes/:id/finalize — button [Finalize] / [Mark as final]
  • POST /api/notes/:id/trash — Move to trash
  • GET /sse — Server-sent events dla hot reload
  • GET /api/list?type=&thread=&status= — JSON variant dla scriptingu
  • GET /api/search?q=... — JSON variant

Co celowo wycięto z v1 viewer.md

  • Tag cloud / /tags — może wrócić w S8+ gdy tagging dojrzeje. Na MVP filtry typu wystarczają.
  • Graph view /graph — KB feature. Po pivocie nie planujemy backlinks między notami.
  • Edit view /n/:id/edit — agenty tylko CREATE (ADR-014). Brak ręcznej edycji w viewerze.
  • "Ask AI to edit" z viewer'a — nie pasuje do append-only.

Performance budget

  • Initial paint: < 100ms (server-rendered + cache headers).
  • Search response: < 50ms dla < 10k notatek (FTS5 BM25).
  • Note view: 0 latency (just serve the file).

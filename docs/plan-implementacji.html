02 Podjęte decyzje (ADR)

Status: Accepted — decyzja stoi · Amended — modyfikowane w v3.1 · Superseded — wycofane · Open — wymaga decyzji

ADR-001Accepted

Bun + TypeScript jako runtime

Single binary, ~10ms startup, native sqlite. Walidacja MCP SDK na Bun przed S3.

ADR-002Accepted

SQLite + FTS5 (rozwinięte w ADR-016)

FTS5 dla search bez external deps. Lekki, single-user OK.

ADR-003Accepted

HTML jako primary format

Standalone HTML files. Validated przez Thariq (Anthropic, 2026-05-08).

ADR-004Accepted

MCP server + OpenClaw Skill (oba)

MCP = uniwersalny tooling. Skill = kiedy/jak używać.

ADR-005Accepted

Eta templates

~6KB, EJS-like, async-friendly. Slot + inheritance.

ADR-006Open / Lean

Folio osobno od Obsidian Vault

Lean: osobno (default). Symlink jeśli ktoś chce. Decyzja: lock-in default.

ADR-007Accepted

HTML sanitization przy zapisie

sanitize-html allowlist. Bez <script>. Style attribute OK na div/span.

ADR-008Superseded

Wersjonowanie do .versions/

Zastąpione przez append-only model (ADR-014). Nie ma edycji — nie ma wersji.

ADR-009PIVOT

Folio = komunikacja, nie storage

Po Thariqu i krytyce v1. KB features wycofane do backloga.

ADR-010Superseded

Variants over history

Zastąpione przez ADR-014 (niezależne dokumenty w thread folder).

ADR-011Superseded

Selection bridge (viewer→agent)

Out-of-scope MVP. Brak edit cycle — nie ma czego zaznaczać do poprawki.

ADR-012Accepted

Dwa profile renderu (standalone/hosted)

Hosted: -50% tokenów via shared theme. Standalone: inline dla publish/share.

ADR-013Accepted, layout open

Cloud publish — osobny projekt

folio.app jako osobne repo. Path vs subdomain — open.

ADR-014Amended v3.1

Append-only + thread folders

Agenty CREATE only. folio.suggest_thread mandatory pre-create. Brak loose notes.

ADR-015Amended v3.1

Lifespan 30d + auto-cleanup

Non-final → .trash po 30d → delete po +7d. Implicit final on publish.

ADR-016Accepted

FTS5 + plain text extraction

Bun HTMLRewriter → text. BM25 z field weights (title ×5, headings ×3, body ×1, tags ×4). Tokenizer PL.

ADR-017Accepted

Analytics od dnia 1

Tabela events. Mierzymy token count, class match rate, lifecycle. Walidacja 50% claim.

ADR-018Accepted

OG screenshot per publish

Playwright na edge → 1200×630 PNG → og:image. Rich preview w Telegram/Slack/iMessage.

ADR-019Accepted

Proactive expiration surfacing (gated)

folio.list_expiring tool + Skill gating (anty-Clippy). Tylko w Folio-related konwersacji.

03 Blokujące decyzje (open)

Decyzje warto podjąć przed wejściem w odpowiedni sprint — żeby nie tracić iteracji.

🔴 Krytyczne · blokuje S0 → S3

Bun + MCP SDK kompatybilność

@modelcontextprotocol/sdk jest TS, ale Bun ma własny module resolver. Niektóre paczki npm mają drobne incompat.

→ bun add @modelcontextprotocol/sdk + smoke test prostego stdio MCP servera w ~15 min → Jeśli fail: plan B = Node z bun-compatible CLI (TS bez build step, ale -50% szybkości startu)
Rekomendacja: walidacja w S0 — nie wchodzić w S3 bez pewności.
🟡 Średnie · blokuje S6 (cloud)

Subdomain layout: path vs subdomain

Adres publikacji jako folio.app/<user>/<slug> czy <user>.folio.app/<slug>?

→ Path-based: łatwiej z certyfikatami (jedno SSL), prostszy routing, gorsze branding. → Subdomain: mocniejsze poczucie „twojej przestrzeni", ale wildcard certs (Let's Encrypt OK, Cloudflare auto).
Rekomendacja: path-based na MVP. Subdomain jako power-user opcja w S7+.
🟡 Średnie · blokuje S6 (cloud)

Auth strategia dla cloud

Magic link, OAuth (GitHub/Google), Sign in with Vercel? Mieszanka?

→ GitHub OAuth dla creatorów (deweloperzy = target audience). → Magic link email dla viewerów (Magda/Łukasz, niedevs). → Sign in with Vercel jako bonus jeśli host = Vercel.
Rekomendacja: GitHub OAuth (creators) + magic link (audience). Sign in z Vercel = nice-to-have.
🟡 Średnie · blokuje S0 startup

Nazwa finalna + dostępność domeny

Folio? Codex? Vellum? Atelier? Coś innego? Domena musi być wolna.

→ Sprawdzić: folio.app, folio.dev, getfolio.app, folio.io. → Backup: vellum.app, atelier.md, codex.dev.
Rekomendacja: 30 min DNS lookup + finalna decyzja. Nie blokuje S1 (lokalnie nie istotne).
🔵 Miękkie · estetyka, nie blocker

Folio vs Obsidian Vault relation (ADR-006)

Lean: osobno (~/Folio/). Czy publish dodatkowo zapisuje stub .md do Obsidian Vault dla cross-linkowania z bazą wiedzy?

→ Osobno, no link: czyste, mniej confusion. Default. → Bridge opt-in: folio config set obsidian.vault ~/Vault + auto-stub .md dla każdego published.
Rekomendacja: default osobno, bridge w backlogu jeśli sam o nim wspomnisz po S5.

S5 Lifespan + auto-cleanup + final marker

Stare niezaznaczone noty same się sprzątają. Final marker via viewer/CLI/MCP.

post-MVP~ 1 tydz
  • Schema: is_final BOOLEAN, expires_at (computed)
  • Cleanup daemon (cron albo lazy on viewer-start)
    Faza 1: !is_final AND age > 30d → .trash/ · Faza 2: .trash/ > 7d → delete
  • CLI: folio finalize, folio unfinalize, folio cleanup --dry-run, folio trash list
  • Viewer: button „Mark as final" + banner „Auto-delete in N days"
  • MCP: folio.finalize({ id })
  • Implicit final on publish: folio.publish → auto is_final=true
  • Config: default_lifespan: 30d w folio.config.json
Exit criteria30+ dni nota !is_final → .trash · is_final=true → zostaje
DependenciesS1 schema (parallel OK z S3)

05 Risk register

Bun + MCP SDK incompat HIGH S0 → S3 Smoke test w S0 (~15 min). Plan B: Node fallback.

OG screenshot pipeline fragility MED S6 cloud Vendor Playwright / Cloudflare Browser Rendering API. Graceful degrade (text-only OG jeśli failure).

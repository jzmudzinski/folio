PostgreSQL vs MySQL vs SQLite dla SaaS

Trzy bazy, jeden mały SaaS. Który wybrać i kiedy. Porównanie z 2026.

flagship

PostgreSQL

Battle-tested, najbogatszy SQL, JSON-first, świetny pgvector dla AI. Defaultowy wybór gdy nie ma silnego powodu inaczej.

workhorse

MySQL / MariaDB

Sprawdzony, prosty operations, najwięcej hosting providerów. Najmocniejszy gdy team ma legacy doświadczenie.

embedded

SQLite

Pojedynczy plik, zero infrastruktury, najszybszy single-user. FTS5 w cenie. Idealny dla offline-first apps.

Plusy i minusy

PostgreSQL

+

  • Najpełniejszy SQL standard + extensions
  • pgvector dla AI workloads
  • JSON-first projektowanie
  • Świetny tooling (Neon branching, Supabase, Aurora)

−

  • Setup connection pooling trochę uciążliwy (pgbouncer)
  • VACUUM management przy wysokim updates traffic

MySQL

+

  • Najpopularniejszy — łatwo znaleźć ops engineerów
  • Najlepsze read-heavy scaling (Vitess/PlanetScale)
  • InnoDB jest battle-tested

−

  • JSON support słabszy niż Postgres
  • Brak pgvector odpowiednika
  • Mniej zaawansowane window functions / CTEs

SQLite

+

  • Zero ops — to plik na dysku
  • FTS5 best-in-class dla full-text
  • Idealny dla local-first / offline-first apps
  • Tania backup strategia (copy file)

−

  • Single writer — concurrent writes blokują
  • Horizontal scaling tylko via Turso/LiteFS
  • Słabszy ekosystem dla SaaS (auth, multi-tenant)

Werdykt

Postgres dla complex schema, AI features, gdy planujesz pgvector. SQLite dla offline-first, single-user apps (CLI tools, desktop). MySQL gdy team ma legacy doświadczenie albo musisz skalować read-heavy traffic via Vitess.

Dla typowego SaaS 2026 z agent/AI features: Postgres na Neon/Supabase. Branching, pgvector, hosted. Brain-dead default.
